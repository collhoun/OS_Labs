# Лабораторная работа №3. Многопоточность и синхронизация

**Вариант 14.** Среднее арифметическое набора 512-битных чисел.

## Задание

В файле хранится набор 512-битных чисел в шестнадцатеричном представлении.
Нужно посчитать их среднее арифметическое и округлить результат до целого.
Обработка выполняется в многопоточном режиме средствами POSIX threads (Linux).
Ключами запуска задаются:

- максимальное число одновременно работающих потоков (`-t`);
- максимальный объём используемой оперативной памяти (`-m`).

## Структура проекта

| Файл | Назначение |
|------|-----------|
| `main.c` | Разбор ключей, чтение файла блоками, очередь задач, запуск потоков, вывод результата |
| `worker.c`, `worker.h` | Разбор текста блока и накопление частичной суммы потока |
| `bigint.c`, `bigint.h` | Арифметика над 512-битными числами (разбор hex, сложение, деление на N, вывод) |
| `gen.py` | Генератор тестового файла: `python3 gen.py <N> <файл>` |
| `check.py` | Эталонный расчёт среднего на Python |
| `small.txt` | Небольшой пример входных данных |
| `Makefile` | Сборка, генерация данных, проверка, замеры |

## Алгоритм

Схема «производитель — потребители» на pthread:

1. Главный поток читает файл блоками по 64 КБ, обрезая блок по границе числа
   (недочитанный «хвост» переносится в следующий блок), и кладёт блоки в
   кольцевую очередь.
2. Рабочие потоки (их число задаёт `-t`) берут блоки из очереди, разбирают
   hex-числа (`parse_hex_512`) и добавляют их в **свой** накопитель.
   Очередь защищена мьютексом и условными переменными
   (`cond_not_empty`, `cond_not_full`). Накопители у потоков раздельные,
   поэтому при суммировании блокировок нет.
3. После конца файла главный поток ждёт рабочих (`pthread_join`)
   и складывает их частичные суммы (`merge_accs`).
4. Сумма делится на количество чисел (`div_acc_by_n`), результат округляется
   до целого и выводится в hex. Накопитель шире 512 бит (`ACC_LIMBS`),
   чтобы сумма не переполнялась.

### Ограничение памяти (ключ `-m`)

Одновременно существуют буферы размера блока: буфер чтения, копия под новую
задачу, по одному в обработке у каждого потока и слоты очереди. Поэтому

    слотов очереди = M / размер_блока - потоков - 2

Чем меньше `-m`, тем короче очередь. При совсем малом лимите уменьшается и
размер блока. Если памяти не хватает даже на минимальную конфигурацию,
программа сообщает об ошибке.

## Полный запуск (с нуля)

Требуется Linux (или WSL), `gcc`, `make`, `python3`.

```bash
# 1. Сборка
make

# 2. Генерация большого файла (по умолчанию 1 000 000 чисел, ~130 МБ)
make big.txt
#    или с другим размером:
make big.txt N=2000000

# 3. Запуск
make run                      # потоков T=4, память M=64 МБ
make run T=8 M=128            # свои параметры

# 4. Проверка корректности: сравнение с эталоном check.py
make test

# 5. Замеры времени для 1, 2, 4, 8, 16 потоков
make bench

# 6. Демонстрация числа потоков
make threads T=4

# 7. Очистка
make clean                    # объектные файлы и бинарник
make distclean                # то же + big.txt
```

Параметры Makefile: `N` — количество чисел в `big.txt`, `T` — число потоков,
`M` — лимит памяти в МБ. Они переопределяются в командной строке.

### То же вручную, без make

```bash
gcc -Wall -Wextra -O2 -pthread -o lab3 main.c worker.c bigint.c
python3 gen.py 1000000 big.txt
./lab3 -f big.txt -t 4 -m 64
python3 check.py big.txt
```

### Ключи программы

```bash
./lab3 -f <файл> -t <потоки> [-m <память, МБ>]
```

| Ключ | Описание |
|------|----------|
| `-f <файл>` | входной файл, числа разделены пробелом или переводом строки |
| `-t <N>` | максимальное число одновременно работающих потоков |
| `-m <MB>` | лимит памяти на буферы данных, МБ (по умолчанию 64) |

### Как читать результат

Программа выводит количество чисел, среднее в hex (`0x...`) и время работы.
`check.py` печатает `N` и `mean` (среднее, округлённое до целого). Значения
должны совпадать с точностью до ведущих нулей: `make test` сравнивает их автоматически.

## Демонстрация числа потоков

`make threads` запускает программу в фоне и показывает число потоков процесса.
Вручную, пока программа работает (для заметного времени работы увеличьте `N`):

```bash
ps -o pid,nlwp,cmd -p $(pgrep lab3)      # nlwp — число потоков (рабочие + главный)
grep Threads /proc/$(pgrep lab3)/status
top -H -p $(pgrep lab3)                  # загрузка по каждому потоку
```

При `-t 4` ожидается 5 потоков: 4 рабочих и главный (он читает файл).

## Исследование ускорения и эффективности

- Ускорение: `S(p) = T(1) / T(p)`
- Эффективность: `E(p) = S(p) / p`

Замеры (`make bench`) на `<13th Gen Intel(R) Core(TM) i5-13420H (2.10 GHz), 8 ядер, Windows>`, файл из 1 000 000
чисел (`python3 gen.py 1000000 big.txt`), `-m 64`:

| Потоков | Время, с | Ускорение | Эффективность |
|--------:|---------:|----------:|--------------:|
| 1 | 0.767 | 1.00 | 1.00 |
| 2 | 0.446 | 1.72 | 0.86 |
| 4 | 0.259 | 2.96 | 0.74 |
| 8 | 0.158 | 4.85 | 0.61 |
| 16 | 0.141 | 5.44 | 0.34 |

Зависимость от размера входных данных (4 потока против 1):

| Количество чисел | Время (1 поток), с | Время (4 потока), с | Ускорение | Эффективность |
|-----------------:|-------------------:|--------------------:|----------:|--------------:|
| 1 000 | 0.001 | 0.001 | 1.00 | 0.25 |
| 10 000 | 0.008 | 0.004 | 2.00 | 0.50 |
| 100 000 | 0.078 | 0.031 | 2.52 | 0.63 |
| 1 000 000 | 0.865 | 0.265 | 3.26 | 0.82 |
| 5 000 000 | 4.264 | 1.259 | 3.39 | 0.85 |

Для 1 000 и 10 000 чисел время сопоставимо с точностью замера (1 мс),
поэтому значения ускорения там оценочные. Небольшие расхождения между
запусками (например, 0.767 и 0.865 с для 1 000 000 чисел) вызваны шумом
замеров, поэтому для итоговой таблицы лучше брать среднее по нескольким запускам.

### Объяснение результатов

По таблице: ускорение растёт до 8 потоков (4.85×), а с 8 до 16 прибавляет
всего 0.3×, эффективность при этом падает с 0.61 до 0.34. Оценка по закону
Амдала даёт долю последовательной части около 10%, что согласуется с
потолком ускорения в районе 5–6×.

- На малых файлах ускорения почти нет: создание потоков и синхронизация
  сопоставимы по стоимости с полезной работой. С ростом файла ускорение
  при 4 потоках растёт с 1.0× (1 000 чисел) до 3.4× (5 000 000), а эффективность
  с 0.25 до 0.85: фиксированные накладные расходы распределяются на больший объём работы.
- Рост ускорения ограничен числом физических ядер, дальше эффективность падает.
- Чтение файла выполняет один главный поток (закон Амдала). При большом
  числе потоков он становится узким местом, рабочие простаивают на пустой очереди.
- Малый `-m` укорачивает очередь, и потоки чаще ждут друг друга.
- Конкуренция за единый мьютекс очереди растёт с числом потоков.
